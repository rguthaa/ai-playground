## Decisions

### DL-001 — Domain: University (committed)
- **Decision:** University domain is committed as the business context for all experiments.
- **Source:** User confirmation in analyst session.
- **Rationale:** Provides realistic workflows, personas, and data shapes without requiring production-grade domain engineering.

### DL-002 — Single-operator, multi-persona
- **Decision:** Platform has a single operator (no auth/tenancy). Multiple university personas (Student, Advisor, Faculty, Admin) are simulated via data/context, not authentication.
- **Source:** User confirmation in analyst session.
- **Rationale:** Avoid auth overhead at this stage; personas exist to make experiments realistic.

### DL-003 — Open-source strategy
- **Decision:** Built on OSS components; platform itself will be published to GitHub. Frontier model APIs (Anthropic, OpenAI) are acceptable exceptions. No proprietary platforms that cannot be self-hosted.
- **Source:** User confirmation in analyst session.

### DL-004 — Growth axes: horizontal + vertical + domain (not infra scaling)
- **Decision:** Platform grows across capability breadth, depth, and domain complexity. Infrastructure/operational scaling is explicitly not a concern.
- **Source:** User confirmation in analyst session.

### DL-005 — Coherence definition
- **Decision:** An experiment is "coherent" with the platform when it shares the same observability layer, evaluation baselines, and domain data — results must be comparable.
- **Source:** User confirmation of analyst-proposed definition.

### DL-006 — MVP scope: GenOS Core + RAG + Evals + Observability
- **Decision:** MVP proves the GenOS architecture is sound via one end-to-end capability experiment (RAG) that is fully observable, evaluated, and traceable.
- **Source:** Derived from brief Section 8; user did not contradict.

### DL-007 — Technology stack
- **Decision:** Python primary for GenAI/orchestration. Java permitted for domain services. LLM-agnostic via GenOS abstraction layer.
- **Source:** User confirmation in analyst session.

### DL-008 — Technology tool choices (OPEN)
- **Decision:** Deferred. Tracing backend, vector store, eval framework, LLM orchestration framework — all open. Architecture phase to resolve.
- **Source:** Brief Section 10 open questions.

### DL-009 — Monorepo vs polyrepo (OPEN)
- **Decision:** Deferred to architecture phase.
- **Source:** Brief Section 10.

### DL-010 — Observability/Tracing/Eval backend: Langfuse
- **Decision:** Langfuse is the selected backend for tracing, observability, and evals in MVP.
- **Source:** User confirmation in PRD session.
- **Rationale:** Open-source, self-hostable via Docker, covers tracing + evals + dashboard in one tool. Eliminates need for custom experiment UI.

### DL-011 — GenOS observability abstraction via OpenTelemetry
- **Decision:** GenOS tracing interface emits OpenTelemetry-compatible signals routed to Langfuse via OTLP config. Domain services never import Langfuse SDK directly.
- **Source:** Architect recommendation accepted by user in PRD session.
- **Rationale:** Ensures switching observability backends costs configuration change, not code change.

### DL-012 — RAG domain data: Synthetic for MVP, extensible
- **Decision:** MVP uses synthetic university data (course catalogs, policy docs, FAQs). Ingestion pipeline designed as pluggable adapters to support real datasets in future.
- **Source:** User confirmation in PRD session.
